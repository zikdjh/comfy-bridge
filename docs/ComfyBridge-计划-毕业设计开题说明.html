ComfyBridge：面向 ComfyUI 的本地与云端 GPU 协同系统

一、课题信息

课题名称 面向 ComfyUI 的本地与云端 GPU 弹性协同系统设计与实现
系统暂定名 ComfyBridge

二、课题摘要

本课题拟设计一套位于本地 ComfyUI 与云端 GPU 之间的协同系统。用户继续使用本地 ComfyUI 界面提交工作流，系统根据任务特征和环境状态，将适合云端执行的任务发送到远程 GPU，并对两端的节点、模型、任务状态和成本信息进行统一管理。

课题拟采用 Python、Web 服务、前端管理界面、关系型数据库和 Modal 云 GPU 等技术路线。开题阶段重点讨论系统是否具有实际价值、技术选择是否合理、功能范围是否可控。

关键词：ComfyUI；云端 GPU；任务分流；环境同步；运行监控；成本控制

三、选题背景与拟解决问题

3.1 ComfyUI 是什么

ComfyUI 是一套面向扩散模型等生成式人工智能任务的节点式工作流工具。用户可以在浏览器中把模型加载、文本编码、采样、图像放大、视频处理、结果保存等操作连接成有向工作流，并通过调整节点参数控制生成过程。与固定表单式界面相比，ComfyUI 更强调流程可组合性和节点复用，适合图像生成、图像编辑、视频生成以及多模型协作等复杂场景。

ComfyUI 本身由前端工作流界面、后端服务、节点执行系统和模型运行环境组成。用户既可以直接使用社区提供的现成工作流，也可以通过安装自定义节点扩展功能。因此，它更接近一个可视化推理编排平台，而不是单一的图像生成软件。

3.2 ComfyUI 怎样运作

ComfyUI 的核心运行方式可以概括为“前端编排、后端校验、图结构执行、事件反馈”四个环节。

  1. 前端编排：用户在浏览器中连接节点、填写参数并形成工作流图。
  2. 任务提交：前端将工作流结构、节点参数和模型引用转换为任务数据，并提交给本地服务。
  3. 后端校验与排队：服务端检查节点是否存在、输入类型是否匹配，并把任务加入执行队列。
  4. 图结构执行：执行引擎按照节点依赖关系依次运行模型加载、采样、解码和输出等步骤，GPU 计算主要发生在模型推理与采样阶段。
  5. 进度与结果反馈：前端通过状态事件获取排队、执行、进度和最终结果，生成文件通常保存在本地输出目录。

这种架构使 ComfyUI 具有较强的扩展能力，但也意味着任务运行同时依赖模型文件、自定义节点、第三方依赖、Python 环境和 GPU 驱动等多个条件。

3.3 ComfyUI 运行需要什么

运行条件 主要内容 对使用者的影响
计算环境 Python、PyTorch、深度学习运行时及图形计算框架。 软件版本和依赖组合会影响节点能否正常运行。
GPU 与显存 通常以 NVIDIA CUDA GPU 为主要运行环境，部分版本也支持其他硬件后端。 显存大小决定可加载的模型规模和生成分辨率，算力决定采样速度。
模型文件 基础模型、LoRA、VAE、文本编码器及其他辅助权重。 模型体积通常较大，对磁盘容量、下载速度和内存管理提出要求。
自定义节点 社区扩展节点及其依赖库。 扩展能力丰富，但容易出现依赖冲突、版本不兼容或环境漂移。
运行服务 本地后端服务、浏览器前端、任务队列和输出目录。 需要持续运行的本地环境和稳定的文件存储。
硬件与电力 GPU、主机电源、散热和长期运行条件。 高性能硬件成本较高，长时间运行会产生电力、噪声和散热负担。

3.4 ComfyUI 的热度与应用基础

ComfyUI 已经成为生成式人工智能应用中较受关注的工作流工具之一。根据 GitHub 公开仓库数据，截至 2026 年 10 月 12 日，ComfyUI 主仓库约有 13.7 万星标和 1.63 万分支，并形成了包括自定义节点、工作流模板、教程和模型生态在内的活跃社区。这一规模说明，围绕 ComfyUI 开展兼容性扩展、云端运行和工程化工具研究具有较广泛的用户基础。

数据来源：GitHub 公开仓库 Comfy-Org/ComfyUI，统计日期为 2026-10-12。

从应用角度看，ComfyUI 的热度不仅来自图像生成需求，也来自工作流复用和节点扩展能力。用户希望将不同模型和预处理步骤组合为稳定流程，但这类流程往往依赖特定设备、模型文件和节点环境，因此也对跨环境运行和资源管理提出了新需求。

3.5 本地运行面临的主要问题

问题 具体表现
硬件成本较高 高性能 GPU 价格较高，个人设备升级周期长，难以覆盖偶尔出现的大模型或高分辨率任务。
显存瓶颈明显 模型规模、批量大小和输出分辨率受显存限制，部分工作流无法在本地完整运行。
算力与时间受限 视频生成、批量采样和多次迭代任务耗时较长，影响调试和创作效率。
环境维护复杂 自定义节点和第三方依赖容易发生版本冲突，工作流复用后可能出现缺节点或运行失败。
模型存储压力大 多个基础模型和 LoRA 可能占用数百 GB 磁盘空间，重复保存和迁移成本较高。
并发能力有限 本地设备通常只能串行执行重型任务，多任务排队时等待时间较长。
远程使用不便 本地服务通常运行在个人电脑上，离开设备后难以继续提交和管理任务。

3.6 Modal 平台的优势

Modal 是面向人工智能与数据计算场景的云端运行平台，提供容器化部署、按需 GPU、持久化存储和编程接口等能力。对于需要弹性算力但又不希望长期维护服务器的个人用户或小团队，它能够将云端资源作为本地设备的补充。

优势 对 ComfyUI 场景的价值
按需使用 GPU 无需购置高性能显卡，任务需要时再申请云端计算资源。
按秒计费、空闲不计费 适合间歇性生成任务，降低长时间闲置带来的成本，但仍需关注网络出口和存储等单独计费项。
容器化运行 可以固定 Python、PyTorch、节点依赖和启动方式，降低云端环境漂移。
持久化卷 适合保存体积较大的模型文件，避免每次启动都重新下载。
弹性扩缩容 任务结束后可以释放计算实例，适合低频或波峰式使用需求。
编程接口与命令行工具 便于与本地管理程序集成，实现任务提交、状态查询和资源管理。
冷启动优化与快照能力 通过镜像和缓存机制减少环境准备时间，为后续性能优化提供空间。

需要说明的是，Modal 的优势并不能自动解决 ComfyUI 的跨端问题。用户仍然需要处理模型分布、节点一致性、任务状态、远端进程管理和费用控制，这些正是本课题需要进一步研究的环节。

3.7 本课题拟解决的问题

本地 ComfyUI 具有操作直接、数据可控和调试方便等优点，而云端 GPU 具有弹性扩容和按需付费的优势。本课题希望把两者组合起来，降低用户在本地与云端之间切换和维护环境的成本。

本课题拟解决的核心问题是：如何在不改变用户原有 ComfyUI 使用方式的前提下，将本地设备与云端 GPU 组合成一套易于使用的生成式人工智能运行环境。

拟解决问题 预期改善
本地算力不足 将高显存或高算力任务转移到云端执行。
云端迁移操作繁琐 由系统统一处理本地与云端的环境差异。
任务状态分散 在统一界面中查看本地和云端任务进度。
云 GPU 费用不透明 提供费用估算、预算提醒和账单对照。
数据外发边界不清 在任务发送到云端前给出明确提示。

四、准备做什么

系统拟完成以下工作，重点是建立本地 ComfyUI 与云端 GPU 之间的透明协同能力，而不是重新开发一套图像生成工具。

4.1 系统目标

目标 拟实现内容
透明接入 用户仍从本地 ComfyUI 界面提交任务，尽量保持原有操作习惯。
任务分流 根据工作流类型、模型、节点、分辨率、预算等因素选择本地或云端执行。
环境协同 检查并同步两端的 ComfyUI 版本、节点、设置和工作流。
模型管理 管理云端模型文件，支持上传、下载、校验和回收。
任务观测 统一展示本地与云端任务的排队、进度、结果和失败信息。
成本管理 估算云端费用，设置预算提醒，并与实际账单进行对照。
安全控制 保护本地管理入口、账号凭据和敏感配置，并提示数据外发。

4.2 系统边界

  • 不修改 ComfyUI 源码，通过现有接口进行协同。
  • 不自行训练模型，也不替代 ComfyUI 的工作流编辑功能。
  • 不把模型文件作为普通配置进行高频自动同步，避免大文件传输成本。
  • 当前面向个人用户或小团队，不以多租户云平台为目标。
  • 预算控制仅约束经本系统提交的云端任务，不等同于云平台账户级预算。

五、准备用什么

本课题拟采用较为成熟、资料充分且易于完成原型验证的技术。下表为初步技术选型，最终方案可根据指导教师意见调整。

技术或平台 拟采用内容 主要用途
ComfyUI 本地工作流与生成执行环境 提供任务提交、工作流编辑和生成结果。
Modal 云端 GPU 与无服务器运行平台 按需启动云端执行环境，提供 GPU 算力。
Python 后端与云端运行逻辑的主要语言 实现任务处理、环境管理和云端执行。
FastAPI 本地 Web 服务框架 提供管理接口、请求转发和状态查询。
HTTP 与 WebSocket 本地服务、ComfyUI 与云端之间的通信方式 提交任务、获取进度和同步运行状态。
React 与 Ant Design 本地管理界面 展示配置、任务、模型、日志和费用信息。
SQLite 轻量关系型数据库 保存任务记录、配置、日志和成本数据。
Git 与自动化测试工具 版本管理与测试 管理开发过程，验证关键功能。

5.1 选择依据

  • 技术生态成熟，便于在毕业设计周期内完成系统原型。
  • 本地与云端均以 Python 为主，能够减少跨语言开发成本。
  • HTTP 与 WebSocket 适合处理任务提交、状态查询和进度推送。
  • SQLite 适合单机原型部署，后续如有需要可替换为其他数据库。
  • Modal 提供按需 GPU，适合验证云端弹性执行的可行性。
