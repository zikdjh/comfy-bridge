3. 逐条明细

LV-01 WS 泵阻塞 HTTP：中断未送达，请求挂到 3600s

  • 现象：中断用例的请求长时间停在 running（>10 分钟）。容器日志显示该 prompt 在云端 0.02 秒就结束了，但桥接器侧始终看不到终态。
  • 根因：Modal web_server 在 WS 泵存活期间只处理这一条连接，其它 HTTP （/history、/queue、/interrupt）排队读超时。云端提前中断且终态事件未被广播 （泵建立晚于广播）时，泵一直挂着 → /history 永远读超时 → 请求被挂到 task_timeout=3600s；/interrupt 同样排队读超时，中断从未真正送达 （日志只剩「云端 /interrupt 失败:」且消息为空）。
  • 决定性对照：桥接器 WS 存活时 GET /history/<pid> → ReadTimeout； 停掉桥接器后同一条 GET /history/<pid> → 200 + 该中断条目。
  • 修复：app/runner/executor.py 的 _track 每 _WS_PROBE_INTERVAL_S=45s 主动收泵 一拍，用权威 /history 判定是否终态，未终态再重挂；interrupt_all 改为 「先收泵 → 发 /interrupt → 跟踪循环稍后重挂」。状态增加 pump / pump_pause_until。
  • 验证：中断用例换种子避免缓存命中并断言 cancelled → 1 passed（11.27s， 记录 status=cancelled duration_ms=8208，日志 POST /interrupt … 200 OK）； 新增 tests/unit/test_executor_track.py（3 项）。
  • 残留观察：见 §5「WS 泵收泵节流」。

LV-02 modal deploy 成功却判失败并回滚 pin

  • 现象：中文 Windows 上点「对齐云端并重建」，UI 报「部署失败，已回滚 pin」， 但镜像其实已构建完成，CLI 退出码为 1。
  • 根因：modal CLI stdout 默认 GBK，成功路径会打印 ✓ / 🔨 / 🎉，触发 UnicodeEncodeError 让进程以非零码退出；调用方据此误判部署失败并回滚版本 pin。
  • 修复：app/modal_volume/client.py 新增 cli_env()（PYTHONUTF8=1 / PYTHONIOENCODING=utf-8 / PYTHONWARNINGS=ignore + 凭证）， app/nodes_mgr/deploy.py、app/cost/modal_billing.py 统一改用；与调用方 decode("utf-8") 对称，顺带修掉中文错误消息乱码。
  • 验证：同一台机器加该环境后 modal deploy 8 秒成功； test_modal_volume_client.py 新增 3 项、test_version_align.py 新增 1 项 （含 test_run_deploy_passes_utf8_cli_env）。

LV-03 热容器读不到 modal volume put 的输入

  • 现象：云端图生图报 node_errors.1: image - Invalid image file: <name>， 而 modal volume ls … input 里文件确实存在。
  • 根因：Modal Volume 是快照语义，外部 volume put 对已在运行的容器不可见。 冷启动容器能读到（探针 /view?type=input 返回 200 / 394894 字节），热容器读不到。
  • 修复：app/runner/client.py 新增 post_input_file()，走运行中容器内 ComfyUI /upload/image（该端点只落原始字节，不做图片解码校验）；executor._upload_inputs 优先走容器内通道，端点不可用时回落 volume put。
  • A/B 实测（同一热容器 ta-01M4MFEG…、同一从未上传过的输入名）： 旧代码 FAILED … Invalid image file；新代码 1 passed，日志 输入已推送云端(comfy): bridge_live_input_v3.png。
  • 验证：新增 tests/unit/test_input_push.py（7 项）。

LV-04 纯 HTTP 请求无终态，永远停在 queued

  • 现象：脚本/集成测试用纯 HTTP 提交本地文生图，请求记录一直 queued， 即使图已写入 output/；状态只由浏览器 WS 中继回写。
  • 修复：新增 app/proxy/local_tracker.py，受理成功后后台轮询本地 ComfyUI /history/<prompt_id>（该端点只在任务结束才出现条目），把 queued → running → done/error/cancelled 收敛到记录；app/main.py 关停时 aclose()。
  • 实测：本地真实出图（RTX 4060，v0.39.2）done / final_backend=local， 生成 bridge_live_local_00002_.png（388715 字节）。
  • 验证：新增 live 用例 test_local_text_to_image（CB_LIVE_LOCAL_FIXTURE_JSON） 与 tests/unit/test_local_tracker.py（8 项）。

LV-05 本地与云端 ComfyUI 版本漂移

  • 现象：本地 /system_stats 报 v0.39.2，云端 lock/comfyui_version.txt 仍 pin 在 v0.38.0；/nodes/version 正确报出 drift。
  • 说明：这不只是配置差异——本地已升级而云端镜像未跟进，会导致节点/算子行为不一致。
  • 修复/验证：UI 真实点击「对齐云端 → v0.39.2」→「开始重建」：state=ok、20 秒完成、 pin v0.38.0 → v0.39.2、history outcome=ok duration_ms=16782；复核 /nodes/version 为 drift=false、pinned=v0.39.2；锁文件 comfyui_version.txt 与 nodes.lock.yaml 同步到 v0.39.2。

LV-06 重启清理把在跑请求写成无时长的 cancelled 僵尸记录

  • 现象：真机过程中重启桥接器后，一条在跑请求 bd506f9e 被启动清理 close_stale_pending() 改写成 status=cancelled，error=桥接重启，执行跟踪丢失， 且没有 finished_ms（duration_ms 为空）。
  • 根因：close_stale_pending() 直接 UPDATE，绕过了 update_status 状态机：
sql  UPDATE requests SET status = 'cancelled', error = ?
   WHERE status IN ('queued', 'running')   -- 不写 finished_ms / started_ms

它假设「桥接重启 = 执行跟踪必然丢失」，对本地请求基本成立，但云端请求 仍在 Modal 上跑，真实结局（成功/失败/取消）并没有被回收。

  • 风险：
    1. 记录缺 finished_ms，时间线与耗时统计出现空洞；
    2. 若云端请求在重启前其实已成功，本地会被永久写成 cancelled， 且输出不会回传——这是数据正确性问题，不只是观感。
  • 修复（2026-10-11，分支 feature/restart-reconcile-modal）：
    1. requests 表新增 modal_pid 列（含老库迁移），云端受理后立即持久化映射， 重启对账不再依赖进程内存；
    2. close_stale_pending() 只关无 modal_pid 的记录（本地跟踪确实丢失）， 云端在跑记录交给新的 app/runner/reconcile.py 启动后轮询 /history 收敛；
    3. 对账三种结局：有终态条目 → 按真实结局回写（done 复用输出回传补媒体库、 error 带详情、interrupted → cancelled）；一直查不到 → 保留 cancelled 但补 finished_ms，error 注明「云端状态未确认」；
    4. 清理关闭的本地记录同样补 finished_ms，不再产生无时长僵尸。
  • 验证：新增 tests/unit/test_reconcile.py（7 项：清理分流、pid 持久化、 成功回传、error 结局、未确认关单、空对账、异步封装）； 全量门禁 369 passed, 10 skipped、ruff 0 违规、mypy 83 文件 0 错误。
  • 真机复测（2026-10-11，隔离实例 8190）：提交云端文生图，modal_pid 落库 （status=running）后强杀桥接器进程模拟崩溃 → 重启 → 对账日志 「重启对账：1 条云端在跑请求待收敛」「云端成功 → done（回传 1 个文件）」， 记录收敛 done 且带 finished_ms（duration ≈ 46.8s），产物 bridge_live_restart_00001_.png（1,614,385 字节）落媒体库可见。 旧代码在同场景下会把该记录永久写成无时长的 cancelled 且不回传输出。

4. 修复计划（已按此实施，2026-10-11）

LV-06：让启动清理区分「本地」与「云端」，并把云端在跑请求收敛到真实结局

目标：重启后不再产生无时长的僵尸记录；云端请求尽量拿到真实终态。

  1. 区分后端：清理时按 final_backend 分流。local 记录维持现有语义 （跟踪确在内存中丢失），但改走 update_status，补上 finished_ms 与 可读的 error（如「桥接重启，本地执行跟踪丢失」）。
  2. 云端补对账：modal 且在跑的记录，启动后入一个轻量对账任务，按 prompt_id 查云端 /history：
    • 有终态条目 → 按真实结局回写（done/error/cancelled，带 finished_ms）；
    • 查不到或云端已缩容 → 保持 cancelled，但补 finished_ms 并在 error 注明「桥接重启，云端状态未确认」。
  3. 回传兜底：对账判为 done 的云端记录，复用现有输出回传路径补齐媒体库文件。
  4. 状态语义：评估是否新增一个显式状态（如 unknown）以区分「确认取消」与 「未知」；若新增，需同步前端状态筛选与成本统计口径。

验收：

  • 新增单测覆盖三种结局（done / cancelled / 查不到）；
  • live 实测：云端请求进行中重启桥接器，重启后记录能收敛到云端真实结局且带 duration_ms；
  • 仪表盘「运行中任务」在重启后不再残留僵尸项。

不改的部分：close_stale_pending() 作为「内存跟踪丢失」的兜底语义保留， 只是不再对所有记录一刀切。

5. 观察项与遗留风险（非缺陷，但需留意）

  1. WS 泵收泵节流（LV-01 修复的副作用）：泵每 45 秒被主动收一拍再重挂， 期间浏览器侧实时进度会有约 3 秒（_PUMP_RESUME_DELAY_S）的抖动窗口。 当前可接受，但若后续要提升实时性，可评估「独立心跳连接」或「先通知再收泵」。
  2. Volume 快照语义是通用约束：任何「外部写卷 → 运行中容器读取」的路径都 会踩同样的坑（输入文件只是最先暴露的一个）。上述 LV-03 修法应作为此类场景的 默认范式：写运行中容器就走容器内端点，volume put 只用于持久化。
  3. 无浏览器场景依赖轮询：LV-04 的终态是轮询收敛，非推送；这与「断言即时状态」 的集成测试假设不同，写测试时需留出收敛延迟。
  4. Modal web_server 单连接处理限制：LV-01 的根因是平台层行为， 我们的收泵是适配而非消除。若 Modal 后续修改该行为，应重新评估收泵频率。
