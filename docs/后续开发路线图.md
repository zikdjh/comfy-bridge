# ComfyBridge 后续开发路线图

> 基线：develop `259b48c`（2026-10-10）
> 适用对象：接手继续开发、准备正式发布或需要安排下一轮迭代的人
> 状态口径：本文件区分「已实现」「已实现但只有降级能力」「只有单测/离线验证」「明确未实现」，
> 不直接沿用旧文档里的完成度标记。

## 1. 当前结论

项目的功能主干已经贯通：本地 ComfyUI 请求拦截、路由决策、Modal 执行、进度中继、
输出回传、请求日志、成本估算、节点/工作流/设置同步、卷管理、打包分发、首次配置向导、
离线兼容矩阵和 Playwright 管理台 e2e 都有对应实现。

第一轮发布收口正在 `feature/license-and-release-docs` 完成。除 live 真机全绿、
安装文档实测和上传/删除等 P1 能力外，不再有未知的发布阻断项：

1. **真机发布验收已形成自动化骨架，仍待真实环境归档**：真实 Modal + 真实 ComfyUI 的
   live 冒烟集已落地，覆盖预检、文生图、图生图、中断、重连、无输出；发布前必须在真实
   两端跑绿并保存结果。
2. **若干规划能力目前是可用但降级的实现**：模型上传没有分块/续传/MD5，删除没有引用检查和
   软删除，节点依赖预检在无法代表目标镜像时只能降级告警，`object_info` 合并策略不可配置，
   任务进度主要靠轮询。
3. **发布与运维材料已补齐，仍待新机器实测**：安装、排障、兼容性文档和 MIT `LICENSE`
   已落地；首次安装到云端首图仍需在干净机器上按文档全流程验收。
4. **架构边界已经明确**：管理 API 已加非回环鉴权保护；SQLite 和大量进程内状态意味着
   单实例假设，Modal CLI 是关键单点，预算护栏是估算而非 Modal 侧硬上限。

## 2. 优先级定义

| 优先级 | 含义 | 处理原则 |
| --- | --- | --- |
| P0 | 不完成就不能对外宣称稳定发布 | 必须真实环境验收，判定标准可复现 |
| P1 | 不阻塞小范围自用，但直接影响完整性和体验 | 纳入下一轮功能迭代 |
| P2 | 扩大使用范围或长期运维前必须处理 | 与发布形态绑定，提前设计 |
| P3 | 工程健康与维护成本 | 随功能迭代分批偿还，不做一次性大重构 |

### P1-4 `object_info` 合并策略可配置

**当前状态（已完成）**

- `bridge.object_info_merge` 支持 `local-first`（默认）、`union`、`local-only`。
- `local-first`：同名 class_type 完全使用本地 schema，只追加云端独有节点和云端模型名。
- `union`：同名 class_type 保留本地结构，把云端独有的模型组合项并入本地模型下拉。
- 云端 class_type schema 只在节点页显式“对比云端 class_type”时拉取并缓存，日常
  `/object_info` 不触发容器冷启动；节点页展示同名节点的字段级冲突路径。
- 配置保存或策略切换后，`/object_info` 内存合并缓存立即失效。

**代码入口**

## 5. P2：运维与规模化前必须处理

### P2-1 管理面鉴权与部署边界

**当前状态（已完成）**

P0-5 已把桥接器从「本机工具」升级到「有明确认证边界的服务」：默认只监听回环、
非回环监听缺令牌拒绝启动、`/api/v1`（health 除外）与 `/bridge` 要求 Bearer/Basic。
P2-1 补齐剩余边界：

- **Origin 校验（CSRF）**：配置令牌后，带 `Origin` 的管理请求做同源比对；跨站来源
  默认 403，可信的前端域名/反代域名经 `CB_ALLOWED_ORIGINS`（逗号分隔）白名单放行；
  无 Origin 的脚本请求仍受令牌约束。
- **审计日志**：`app/core/audit.py` 写 JSONL 到 `<配置目录>/audit.log`（可用
  `CB_AUDIT_LOG` / `CB_AUDIT_LOG_PATH` 覆盖），把**写操作**与**所有 401/403 拒绝**
  记录为 方法/路径/状态码/客户端 IP/Origin/认证方式/原因；成功的只读请求不记，
  且**绝不落 Authorization、token 或请求体**。超 5MB 轮转一份 `.1`。
- **部署边界文档**：新增《反向代理与多用户部署》，写明管理面 vs 数据面边界、令牌
  配置、Origin 白名单、审计说明、Nginx 反代示例（含 `Host`/`X-Forwarded-Proto`/
  `X-Forwarded-For` 透传与 SSE/WS 超时）和部署前检查清单。

### P2-3 Modal CLI 单点与凭证失效处理

**当前状态（已完成）**

- `modal_volume.client` 统一把失败分类为「未安装 / 未登录 / 网络失败 / 权限不足 /
  远端状态不确定 / 命令失败」，每类附带 `retryable` 与可操作的 `next_action`。
- 只对 `app list`、`volume ls/get` 等只读命令在网络错误时退避重试一次；写操作不
  自动重发，避免重复上传、删除或部署。
- 最近一次失败和最近成功时间保留在进程内，`GET /api/v1/health/modal-cli` 返回
  CLI 路径、版本、登录状态、`app list` 延迟、应用状态和最近失败。
- 管理台新增「系统状态」页，展示自检结果、五类错误说明、最近失败与处理建议，并
  提供手动重新自检。

**实现结果**

- 分类采用保守文本匹配：无法确定的错误归为 `command`，超时归为 `uncertain`，
  不把普通命令错误误报成权限或登录问题。
- 自检接口不阻塞管理台启动；CLI 缺失或未登录时返回结构化错误而不是 500。
- 诊断状态是单实例进程内状态，后端重启后清空；与 P2-2 的单实例边界一致。

**代码入口**

- `backend/app/modal_volume/client.py`
- `backend/app/api/v1/health.py`
- `frontend/src/api/health.ts`
- `frontend/src/pages/status/index.tsx`
- `frontend/src/components/layout/Shell.tsx`

**验收标准**

- CLI 缺失时状态页显示「未安装」并给出安装命令。
- token 失效时显示「未登录」并给出 `modal token new` / 设置页两条路径。
- 只读网络失败自动重试一次；写操作一次失败即返回，不重复执行。
- 状态页能看到最近一次失败的建议动作，不要求用户从原始 CLI 日志猜原因。
