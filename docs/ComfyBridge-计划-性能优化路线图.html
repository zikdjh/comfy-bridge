1 目标与范围

本计划把性能优化从“感觉更快”落为可测量、可复现、可验收的工程项。范围覆盖 ComfyBridge 桌面启动、管理台交互、请求受理、云端接力、资源占用与发布门禁，不覆盖 Modal 云端 GPU 的绝对执行时间和 ComfyUI 本体渲染耗时。

用户目标双击后快速出窗口，页面操作无卡顿，提交云端不阻塞。
系统目标受理链路 p95 < 500ms，审计不拖慢主路径，空闲资源稳定。
工程目标性能数据可采集、可对比、可进 CI，不允许只靠肉眼判断。

1.1 明确不做的优化

  • 不为了压启动时间移除依赖完整性检查。
  • 不在后台默默常驻 Modal 容器，以避免无成本提示的资源占用。
  • 不用同步阻塞调用换“更快看起来完成”的假象。
  • 不在本地做真实生图性能基准，云端生图一律走 Modal。

2 性能预算

以下预算分为“已存在门禁”与“首版预算”。首版预算用于 beta.4 建立基线，允许在真实数据采集后调整一次，但不允许无记录地反复放宽。

桌面热启动双击到窗口可交互 < 1.5s首版预算同一机器连续启动，排除磁盘冷读

预算不是产品承诺，而是回归门禁。若实际机器达不到，需要先区分“机器基线差异”与“代码回归”，再调整预算。

3.1 度量面

层级指标工具用途

前端交互路由切换、首屏加载、长任务、重复请求、内存Playwright trace、浏览器 Performance识别渲染与请求问题

持久化SQLite 查询耗时、审计写延迟、磁盘 I/Opytest、trace、磁盘计数器防止日志拖慢业务

资源占用CPU、RSS、句柄、端口、线程进程采样脚本发现泄漏与失控轮询

3.2 采集原则

  • 同一指标至少跑三次，报告 p50、p95，不使用单次最优值。
  • 冷启动与热启动分开统计，不混在一起。
  • 开发机、CI、发布机分别建立基线，避免用 CI 绝对值判断本机体验。
  • 每次优化前后都保留同一套环境数据，形成对比记录。
  • 性能数据只入 `docs/` 或测试报告，不把用户私有工作流带入仓库。

5 桌面启动

5.1 现状

桌面启动器已实现 Tauri 窗口、内置 Python 后端、端口探测与进程树清理。当前短板是缺少标准化启动耗时数据，也未区分冷启动、热启动和后台依赖初始化。

5.2 优化项

  1. 埋启动阶段日志：进程启动、runtime 检查、后端 spawn、端口 ready、窗口创建、页面加载完成。
  2. 并行化初始化：`inspect_bundle()` 与 `desktop_listen()` 可并行，避免串行文件探测。
  3. 窗口骨架先显示：创建窗口时先展示加载骨架，再等待后端 ready 后恢复页面。
  4. 后端启动阶段瘦身：拆分必须同步导入与可异步导入模块，降低 `python -m app.cli` 初始 CPU。
  5. 静态资源预热：Tauri 窗口启动后立刻预取 `/bridge/` 主资源，避免窗口空白等待。
  6. 失败路径提效：端口占用、runtime 缺失时直接弹窗，不等待超时。

5.3 验收

  • 同一机器 3 次冷启动均满足冷启动预算。
  • 同一机器 3 次热启动均满足热启动预算。
  • 启动失败路径不出现窗口空白或控制台窗口。
  • 关闭窗口后端口与进程树释放时间满足预算。

6.2 优化项

  1. 建立页面切换基准：记录每个菜单的导航耗时、请求瀑布、主线程长任务。
  2. 路由级代码分割：按页面拆 chunk，减少首屏 JS 体积。
  3. 列表虚拟化：日志、媒体库、模型卷等长列表改虚拟滚动。
  4. 轮询治理：按页面可见性降频，不可见页面停止刷新。
  5. 请求去重：同一数据在短期内只允许一个在途请求，后续复用结果。
  6. 表格渲染优化：复杂表格做列级 memo，避免整表重渲。
  7. 加载态分级：数据未就绪时展示结构化骨架，不阻塞整个页面。

6.3 验收

  • 所有主页面切换满足预算。
  • 同一页面 5 分钟内不出现 CPU 空转。
  • 长列表滚动无明显掉帧，交互期间主线程无连续阻塞任务。
  • Playwright trace 中没有重复且无必要的串行请求。

7 云端受理链路

7.1 现状

已有 `P-08` 云端提交受理基准，目标 p95 < 500ms。当前重点是守住这条门禁，并把“受理”与“云端执行等待”分开统计。

7.2 优化项

  1. 受理链路分段打点：规则匹配、预检、落库、派发、应答。
  2. 缓存节点与模型在场结果，避免每次请求重新扫描。
  3. 审计写、请求日志、图快照全异步化，不占主路径。
  4. 连接池复用：HTTP、WS、Modal 客户端统一连接生命周期。
  5. 输入文件预上传改为并行分块，只在确实缺失时触发。
  6. 预检失败降级路径明确，不因网络抖动阻塞提交。
  7. 云端等待状态可取消，UI 显示等待阶段而不是静默。

7.3 验收

  • 受理 p95 保持 < 500ms，p99 不超过 1s。
  • 同一输入在缓存有效期内不重复扫描。
  • 审计开关对受理 p95 差值 < 20ms。
  • 云端请求终态与产物回传路径不受性能优化影响。

8 资源与稳定性

8.1 优化项

  1. 空闲轮询降频：页面不可见、任务无变化时减少网络请求。
  2. 后台任务限流：同一类任务使用单飞和队列，避免重复执行。
  3. 日志写入合并：批量提交 SQLite 和审计写，降低 fsync 频率。
  4. 缓存失效精细化：配置、节点、模型、状态各自独立失效。
  5. 连接生命周期治理：避免短周期创建与销毁 HTTP/WS 客户端。
  6. 进程树资源审计：定期检查线程数、句柄数、内存增长。

8.2 验收

  • 桌面应用空闲 CPU 与 RSS 达预算。
  • 连续运行 30 分钟无句柄泄漏和端口残留。
  • 日志量增长不导致受理延迟线性上升。
  • 关闭窗口后 Python 进程树全部退出，无孤儿进程。

9.3 CI 策略

  • 性能阈值必须进 CI，不能只在文档中说明。
  • CI 的绝对耗时允许与本机不同，但回归比较必须有固定环境。
  • 性能测试失败与功能测试失败同等阻塞合并。
  • 每次发布前输出一份“性能基线对比表”。

10 风险与对策

风险等级对策
优化启动时误削弱完整性检查高启动阶段仍强制检查 runtime、GUI 和应用包，只优化顺序与并行度
页面拆分导致懒加载抖动中主页面预加载，非关键页面懒加载
异步审计丢日志高异步队列必须有失败重试与关闭前 flush
缓存导致路由决策过期高所有缓存必须有明确 TTL、失效事件与强制刷新入口
CI 抖动造成误报中采用相对阈值与多轮采样，必要时允许 retry
长列表虚拟化破坏语义中保留筛选、分页与操作状态测试，先在日志页试点

11 执行顺序

  1. 建立启动、首屏、受理、空闲资源四类基线数据。
  2. 把 P-06、P-08 与新增性能检查接入 CI。
  3. 优先优化桌面启动与页面切换。
  4. 再做受理链路分段与异步化。
  5. 最后做资源占用与长期运行治理。
  6. 每次发版前输出性能对比报告，并同步更新本文预算与结论。
