2. 本轮修复记录

R2-01 透传 Origin 不改写导致 403（P1）

发现路径：多组提示词 Playwright 验证（frontend/e2e/multi-submit-verify.spec.ts） 全部走 /prompt + JSON 正常提交；图格式提交走 _forward_raw 兜底，此前盘点 （见《真机验收缺陷清单》§5 观察项之外）发现该路径未复用 forward_request 的 Origin/Referer 改写逻辑。

根因：prompt_submit._forward_raw 自拼转发头，只剥离了 host/content-length/ connection 等逐跳头，没有把 Origin: http://127.0.0.1:8189 改写为上游地址。 ComfyUI server.py 的 create_origin_only_middleware 对回环地址校验 Host == Origin，8189 ≠ 8188 → 403。

修复：

  • app/proxy/passthrough.py：抽出公共函数 upstream_headers(request)， 剥离逐跳头 + Origin/Referer 改写为上游 authority；forward_request 改为复用。
  • app/proxy/prompt_submit.py：_forward_raw 改用 upstream_headers。
  • 新增 tests/unit/test_passthrough_origin_headers.py：2 项断言改写与剥离。

验证：pytest tests/unit/test_passthrough_origin_headers.py tests/unit/test_privacy_confirm.py -q → 17 passed。

防回归：透传头改写逻辑此后只有一处实现（upstream_headers），新增转发路径 一律复用，避免再出现双份逻辑漂移。

批次 2：性能补测（P2）

  • R2-03 P-06 审计日志写入延迟：新增 tests/perf/test_p06_audit_latency.py

（audit 开/关对照各 200 次并发写 + 30 次热身）。结果：audit on p50/p95 = 7.5-7.7/9.4-10.3ms，off p50/p95 = 3.5-3.7/5.0-5.8ms，delta p95 ≈ 4.3-4.7ms， 远低于 20ms 拖累阈值 → 结论「审计写入不拖累主链路」，无需改异步。

  • R2-04 P-08 云端 /prompt 提交延迟：新增 tests/perf/test_p08_cloud_submit_latency.py

（100 次受理路径基准，executor.dispatch 桩化；云端真实往返由 live smoke 覆盖）。 结果：p50/p95/mean = 1.20/1.52/1.26ms，p95 < 500ms 目标大幅富余 → 结论「受理路径无瓶颈」。两轮数值已同步《第二轮完整测试计划》第 8 节。

批次 3：真机验收残留（P2，需云端环境）

  • R2-05 大文件分块续传（真实 Modal，2026-10-11）：

120MB 随机文件（MD5 e04647bd…），15 块 × 8MB，隔离桥接器 8190 + 真实 comfyui-data 卷。链路：init → 传 4 块（32MB）→ 强杀桥接器进程 → 重启 → 会话从磁盘恢复（uploaded_chunks=[0..3]，missing_count=11，与杀前一致） → 补传 11 块 → complete（合并 + 整文件 MD5 校验通过）→ volume put 落卷 → volume get 拉回比对 MD5 一致。测试文件与本地临时目录已清理。 单测覆盖见 tests/unit/test_model_uploader.py（7 项）。

  • R2-06 软删除/恢复/到期清理（真实卷，2026-10-11）：隔离桥接器 8190 +

真实 comfyui-data 卷，100KB 演示文件 models/checkpoints/bridge-trash-demo.bin： ① dry_run 引用检查返回 checked/referenced=false；② 真删 → 软删除落 .trash/20261011T122343Z/...，原路径消失；③ trash list 可见；④ restore → 原路径恢复，volume get 拉回 MD5 一致（4ad1fef6…）；⑤ 伪造过期时间戳 .trash/20250101T000000Z → cleanup_all_expired_trash() 精确删除它并保留 当日目录；⑥ purge 精确删除回收站内文件（目录壳保留）；恢复后的源条目 不存在时 purge 返回 ok:false（优雅降级）。两个观察项：恢复是移动语义 （回收站内源条目消失，UI 无需二次清理）；purge 只收 .trash/<ts>/ 下的 具体路径，整时间戳目录走过期清理（-r 递归）或 CLI。测试残留已全部清理。

  • R2-07 安装态验证（同机隔离，2026-10-11）：真「干净机器」项受开发机限制，

按「wheel 构建 → 隔离 venv 安装 → 全新配置目录启动 → 首图」做了安装态全链路： build_package.py 产出 comfy_bridge-0.1.0-py3-none-any.whl（99 文件，自检 GUI/runner 副本齐）；venv pip install 成功（wheel 依赖闭包完整，含 modal 1.6.1）； comfy-bridge --help 可用；CB_CONFIG_DIR=全新目录 + --port 8191 启动 → 首次创建配置（注意：config.toml 延迟到保存配置时生成，首次即建目录）； /bridge/ 管理台 HTML 正常；/object_info 代理 200；本地首图 done （17.8s，rule_trace 默认 local，请求记录/图快照/节点在场缓存正常生成）。 观察项（非阻断）：① 安装态无 modal CLI 时启动警告「回收站清理无法列卷」， 与文档「仅本地桥接可暂不配置 Modal」一致但建议降噪为首次运行提示； ② 未配置 web_url 时节点在场刷新报 protocol 缺失，建议静默跳过直至配置完成。 严格 30 分钟干净机计时仍需真新机器/VM；wheel 与依赖闭包已就绪，剩余人工步骤 （Modal token、proxy auth、部署 Runner）均为文档既有流程。

批次 4：方案决策（P3）

  • R2-08 方案A 只读探针（2026-10-11）：结论不投入。决定性发现——

原生 /api/jobs 条目（v0.39.2 comfy_execution/jobs.py）没有工作流名， 注入云端任务后原生面板只能显示 workflow_id 或空；且面板对 synthetic 条目的取消按钮无效（本地队列无该 id）。悬浮面板（方案B）显示真名、 不依赖原生私有 schema、升级兼容性好，为长期形态。两条低成本增强 （悬浮行取消按钮、按队列序排序）纳入后续小修。完整评估见 ComfyBridge-过程-方案A探针-原生JobQueue.html。
