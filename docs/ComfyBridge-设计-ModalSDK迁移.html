1. 背景与目标

当前后端与 Modal 控制面的全部交互（卷操作、应用状态、账单查询、部署）都走 modal CLI 子进程。这是历史决策：早期为规避「后端主进程 import modal SDK 的副作用」与「代理链路问题」而选择子进程隔离。

CLI 路线在真机运行中暴露出一类系统性成本——文本面：所有结果都从 stdout 解析而来，已经积累了一串 quirk 修复：

  • GBK / UTF-8：modal deploy 成功路径打印 ✓ / 🔨 / 🎉， 中文控制台默认 GBK 触发 UnicodeEncodeError，进程以非零码退出， 曾导致「部署成功却判失败并回滚版本 pin」（LV-02，见《真机验收缺陷清单》）；
  • 双重转义：volume ls --json 对非 ASCII 文件名先转义一次、 json.loads 后名字仍是字面 \uXXXX 序列， 需要 _unescape_cli_name() 还原；
  • banner 混入：CLI 输出混有 DeprecationWarning 等日志行， cli_json_list() 只能靠「定位首个 [」截取 JSON 数组；
  • 错误分类靠文本匹配：_classify_error() 对 stdout/stderr 做 关键字匹配（"rate limit"、"401"、"connection refused"...），无法确定的归为 command，天然保守且有漏判面；
  • 子进程开销：每次调用 fork 一个 Python 解释器（启动期首检、30s 轮询的账单查询、 逐节点上传都要反复付出）；超时需强杀子进程，远端状态不确定。

目标：控制面数据操作（卷读/写/删、卷 CRUD、应用状态、账单查询）改为 Modal Python SDK 直调，消除文本解析层与子进程开销；保留类型化错误分类、 只读退避重试、诊断留痕三件套契约。modal deploy、两处 modal run 流式作业与 container list/stop 在 P1 保留 CLI （理由见 §5 批次 4），P2 再评估。

红线不变：凭证只存 ~/.comfybridge/config.toml 或环境变量， 绝不写入代码库、命令回显或提交；API 响应对凭证一律掩码。

凭证与客户端

await modal.Client.from_credentials(token_id, token_secret) 与 await modal.Client.from_env() 均为 async classmethod；所有对象方法 （from_name / objects.* / lookup / from_context）都接受 client=... 注入。这正好承接现有 auth_env() 的语义：

python# 未配置 → from_env()（回落 ~/.modal.toml，与 CLI 行为一致）
# 已配置 → from_credentials(token_id, token_secret)（与 auth_env 注入等价）
# 账号切换 → 重建 client，替代 reset_runtime_state() 清诊断的联动点

proxy_credentials()（runner 端点代理鉴权凭证，纯配置读取）与 volume_name() 原样保留——它们是配置面函数，不涉及 CLI 子进程。 auth_env() 在 launch.py 三处独立子进程仍在用（批次 2 收敛前）， 迁移后它仍被三条保留 CLI 的路径依赖：cli_env() 内部展开 （deploy 与 _popen 流式作业都经它）、launch.py:127,222,308 的容器管理，以及 version_align.py:26 的边界引用 （noqa: F401，供 test_version_align 断言同一 env 边界）。 因此 auth_env / cli_env 都不在批次 4 的删除范围内。

4. 目标架构与模块设计

不新建平行模块：modal_volume/client.py 是全部调用方的既有缝隙， 原地把它从「CLI 子进程封装」改造为「SDK 网关」，公开类型化函数， 调用方分批从 run("volume", ...) 命令串迁到类型化调用。

4.1 模块内部结构

  • client 生命周期：进程内缓存一个 client（按凭证对缓存）； from_credentials 失败回落 from_env； 账号切换钩子（config API 的既有 reset_runtime_state() 联动点， api/v1/config.py:129）重建 client 并清诊断。 Volume 句柄一并缓存：Volume.from_name 是懒 hydrate， 首次使用多一次 RPC，而 usage.py 的用量 BFS 会对同一卷发起几十次 listdir → 按 (client, volume_name) 缓存已 hydrate 句柄， 与 client 同生命周期、账号切换一起失效。
  • 类型化函数面（保持既有函数名优先）： list_dir / list_files / volumes_list / volume_create / volume_delete / put_file / put_directory / get_file / remove_file / app_status / billing_summary / billing_report。其中 put_file / put_directory 是网关自有函数名， 内部实现走 async with vol.batch_upload(force=...)； 另加 put_many(items) 让节点批量上传 / manifest 写入合并成一次提交。 每个类型化函数保留 timeout 形参（默认 600s）： health 传 15s/20s、uploader.py:433 传 24h， asyncio.wait_for 需包住整个 async with 块。
  • 返回形状归一（批次 1 的决定项）：list_dir / list_files 继续返回既有 dict 形状，让 15 处消费者与前端零改动， 归一规则按 CLI 同源实现逐字对齐： name = entry.path 剥查询前缀（沿用现逻辑）； type = FileEntryType.DIRECTORY→"dir"、 SYMLINK→"link"、其余 →"file" （对齐 cli/volume.py 的 filetype 映射）； size = humanize_filesize 等价实现 （1024 基，"6 B" / "1.2 MiB"，B 无小数、其余一位小数）； mtime = 本地时区 %Y-%m-%d %H:%M %Z （等价 timestamp_to_localized_str(ts, False)）， mtime <= 0 落空串——现路径 str(None) 会产出字面 "None"，顺手修掉。 同时新增整数字段 size_bytes / mtime_s： usage.py:134 现在要用 parse_size 把字符串解析回字节， 改读 size_bytes 后该函数与 _SIZE_RE/_SIZE_UNITS 在批次 4 一并退役。前端 api/volume.ts 的 size: string / mtime: string 与表格列（volume/index.tsx:637-638） 因此不动。
  • 错误映射：SDK 异常 → 既有 ModalCliError 分类契约 （category / label / retryable / next_action / command / exit_code 字段与分类枚举不变，前端「系统状态」页结构零改动）： NotFoundError → uncertain（含 retryable 判定）、 AlreadyExistsError / ConflictError → command（409 语义由 API 层保留）、 AuthError → not_logged_in、 PermissionDeniedError → permission、 ConnectionError / TimeoutError → network（retryable； 注意二者是 modal.exception 自有类型，遮蔽内建同名异常， 导入时需限定命名空间）、 ResourceExhaustedError → rate_limited（retryable； 这就是 gRPC RESOURCE_EXHAUSTED / 429 的正主， 不必再靠文本匹配 "rate limit"）、 InvalidError / VersionError / ClientClosed → command。 映射表带保守兜底：未知异常归 command，不误报登录/权限。 文案需随语义更新（属前端可见变更，非结构变更）： _DEFAULT_ACTIONS["not_installed"]「安装 modal CLI…pip install modal」、 uncertain「先用 modal app list 核对远端状态」、 health.py「找不到 modal CLI（请安装：pip install modal…）」、 前端 models/index.tsx:204「本机未找到 modal CLI / 同步通过 modal CLI 执行」 都是 CLI 口径，批次 3 一并改为 SDK 口径。 保留 CLI 的路径（deploy / 流式 run / container）错误分类维持现状 （直接构造 ModalCliError，不做文本分类）。

4.4 同步 / 异步边界

SDK 的对象方法都是协程或异步上下文管理器，而现网有三类调用形态，迁移时分别处理：

  • 本来就是 async 的调用方（绝大多数：nodes.py、 volume.py、usage.py、settings_sync.py、 workflows_sync.py、api/v1/workflows.py、 precheck.py、uploader.py、health.py、 runner/client.py）：直接 await 类型化函数，调用形态不变。
  • 同步函数 + asyncio.to_thread 包裹： launch.py:118 _push_modal_args（由 write_launch 在 178 行 await asyncio.to_thread(...) 调用）。批次 2 收敛时 把它改成 async 并直接 await——外层已经是协程，再套一层线程会让 async with batch_upload() 无处安放。
  • 保留 CLI 的同步路径：launch.py 的 _container_rows / _list_modal_containers / _stop_modal_containers 与 _popen 流式作业（downloads.py:164、 moves.py:174、deletion.py:237、 jobs.py:153,160）继续 subprocess + to_thread， 不引入 SDK，因此 _popen / cli_env / auth_env 必须留在网关里 （见 §5 批次 4 的删除清单修正）。

兜底：若批次 1 真机验证发现 uvicorn 事件循环与 modal grpclib 客户端不兼容， SDK 调用整体收敛到独立 loop 线程（run_coroutine_threadsafe）； 此时前两类调用方仍只见 await，边界不外泄。

6. 风险与对策

风险对策
Windows 事件循环：uvicorn asyncio loop 与 modal grpclib 客户端共存未验证 批次 1 首个验证项：真机跑一次 listdir + health 自检，观察 "Event loop is closed / already running"；兜底方案：SDK 调用收敛到 独立 loop 线程（run_coroutine_threadsafe），语义不变。 实测依据：modal 1.5.5 import 不设事件循环策略，风险主要在运行期。
主进程 import modal 的副作用（modal-client logger、配置读取） 懒导入收敛在网关模块；logger 为独立命名空间，必要时 logging.getLogger("modal-client").setLevel(WARNING)； pytest 收集路径确认不触发网络调用。
多账号凭证切换：进程内 client 缓存与账号注册表联动 凭证对作为 client 缓存键；账号激活钩子重建 client； 切换期间在途调用允许完成（client 独立对象，不复用全局状态）。
语义差异引入回归：mtime 单位（CLI 文本 vs SDK int）、 size 类型（str vs int）、listdir 根路径、--force 覆盖、 staging 排除 已定案为网关内形状归一（§4.1）：size/mtime/type 按 CLI 同源格式重建成字符串并额外提供整数字段，前端与 15 处形状消费者零改动； 差异清单显式列在批次 1/2 测试用例里，并以真实 CLI 输出做 golden 对照； 前端展示层（大小/时间格式化）逐项过一遍 e2e。
batch_upload 的提交面：错误集中在 __aexit__， 批量上传的部分失败语义与 CLI 逐文件不同；只读卷直接抛 InvalidError 网关把整个 async with 包进 asyncio.wait_for 与 错误映射；put_many 失败时按批报错并保留每项的 local/remote 上下文（对齐现有 precheck / nodes 的 failed[] 结构）；写操作一律不自动重试（沿用 _READ_ONLY_OPS 判据）。
app_status 依赖内部 stub （client.stub.AppList + api_pb2），属非公开 API， modal 升级可能改 proto 字段 按既有「实现偏差」口径登记在 client.py 注释与本文档； modal 版本在 pyproject 锁死，升级走 version_align 同款流程；启动自检对 AppListRequest/AppStats.description/state 做一次存在性断言， proto 变更即刻暴露而不是静默返回 None。
SDK 侧新增入参校验：billing cycle 非 UTC 月初 / 未来月、 路径尾缀 */**、remote_path 尾缀 / 都会抛 InvalidError/ValueError， CLI 时代部分场景是静默容忍的 映射表覆盖 InvalidError → command（不自动重试）； 批次 1/2 用现有真实参数跑一遍边界（current_cycle()、 回收站路径、.keep 标记写入）确认无新增抛错。
错误分类漏判：SDK 异常类型比 CLI 文本更结构化，但部分错误 （服务端 5xx、限流）需确认异常形态 保守兜底（未知 → command）沿用；限流改按异常类型判定 （modal.exception.ResourceExhaustedError = gRPC RESOURCE_EXHAUSTED），文本匹配只作补充； 注意 ConnectionError / TimeoutError 是 modal 自有类型、 遮蔽内建同名异常；真机触发一次限流验证 1s/4s/10s 退避路径仍生效。
双轨期语义分裂：批次 1-3 期间 SDK 面与保留 CLI 面 （deploy / 流式 run / container）并存，同一个 ModalCliError 可能来自两条路径，诊断字段口径不同 诊断留痕统一在网关入口打点（含 transport: "sdk" | "cli" 标记，仅进日志不进 REST 响应）；保留 CLI 路径的错误分类维持现状 （不做文本分类），避免两套分类规则互相污染。
打包体积：modal 已是依赖，无新增；但 SDK import 链更重 （grpclib、protobuf） wheel 打包自检沿用 build_package.py； pipx 安装态真机跑一次启动 + 首图。
health 端点与前端契约变更：path/found/cli_found 字段语义变化， 前端状态页与模型页需同步 批次 3 显式处理（§4.2）：字段名保留、语义与文案更新； Playwright e2e 确认状态页与模型页不回归； 端点名 modal-cli / TS 类型 ModalCliHealth 暂不改名， 避免路由与 queryKey 联动面扩大。 app_state 字符串与 latency_ms 语义同批处理： 前者必须与 CLI 逐字一致（前端有两处 === "deployed" / === "stopped" 硬比较）， 后者不再含子进程启动开销，数值会明显下降——属预期改善， 需在验收口径与状态页说明中讲清，不要当回归处理。
