1. 背景与目标

当前后端与 Modal 控制面的全部交互（卷操作、应用状态、账单查询、部署）都走 modal CLI 子进程。这是历史决策：早期为规避「后端主进程 import modal SDK 的副作用」与「代理链路问题」而选择子进程隔离。

CLI 路线在真机运行中暴露出一类系统性成本——文本面：所有结果都从 stdout 解析而来，已经积累了一串 quirk 修复：

  • GBK / UTF-8：modal deploy 成功路径打印 ✓ / 🔨 / 🎉， 中文控制台默认 GBK 触发 UnicodeEncodeError，进程以非零码退出， 曾导致「部署成功却判失败并回滚版本 pin」（LV-02，见《真机验收缺陷清单》）；
  • 双重转义：volume ls --json 对非 ASCII 文件名先转义一次、 json.loads 后名字仍是字面 \uXXXX 序列， 需要 _unescape_cli_name() 还原；
  • banner 混入：CLI 输出混有 DeprecationWarning 等日志行， cli_json_list() 只能靠「定位首个 [」截取 JSON 数组；
  • 错误分类靠文本匹配：_classify_error() 对 stdout/stderr 做 关键字匹配（"rate limit"、"401"、"connection refused"...），无法确定的归为 command，天然保守且有漏判面；
  • 子进程开销：每次调用 fork 一个 Python 解释器（启动期首检、30s 轮询的账单查询、 逐节点上传都要反复付出）；超时需强杀子进程，远端状态不确定。

目标：控制面数据操作（卷读/写/删、卷 CRUD、应用状态、账单查询、容器管理）改为 Modal Python SDK 直调，消除文本解析层与子进程开销；保留类型化错误分类、 只读退避重试、诊断留痕三件套契约。modal deploy 与两处 modal run 流式作业在 P1 保留 CLI（理由见 §5 批次 4）。

红线不变：凭证只存 ~/.comfybridge/config.toml 或环境变量， 绝不写入代码库、命令回显或提交；API 响应对凭证一律掩码。

凭证与客户端

await modal.Client.from_credentials(token_id, token_secret) 与 await modal.Client.from_env() 均为 async classmethod；所有对象方法 （from_name / objects.* / lookup / from_context）都接受 client=... 注入。这正好承接现有 auth_env() 的语义：

python# 未配置 → from_env()（回落 ~/.modal.toml，与 CLI 行为一致）
# 已配置 → from_credentials(token_id, token_secret)（与 auth_env 注入等价）
# 账号切换 → 重建 client，替代 reset_runtime_state() 清诊断的联动点

proxy_credentials()（runner 端点代理鉴权凭证，纯配置读取）与 volume_name() 原样保留——它们是配置面函数，不涉及 CLI 子进程。 auth_env() 在 launch.py 三处独立子进程仍在用（批次 2 收敛前）， 迁移后该函数仅剩 deploy/run/container 保留 CLI 的路径引用。

4. 目标架构与模块设计

不新建平行模块：modal_volume/client.py 是全部调用方的既有缝隙， 原地把它从「CLI 子进程封装」改造为「SDK 网关」，公开类型化函数， 调用方分批从 run("volume", ...) 命令串迁到类型化调用。

4.1 模块内部结构

  • client 生命周期：进程内缓存一个 client（按凭证对缓存）； from_credentials 失败回落 from_env； 账号切换钩子（config API 的既有 reset_runtime_state() 联动点）重建 client 并清诊断。
  • 类型化函数面（保持既有函数名优先）： list_dir / list_files / volumes_list / volume_create / volume_delete / put_file / put_directory / get_file / remove_file / app_status / billing_summary / billing_report。
  • 错误映射：SDK 异常 → 既有 ModalCliError 分类契约 （category / retryable / next_action / command 字段不变， 前端「系统状态」页零改动）： NotFoundError → uncertain（含 retryable 判定）、 AlreadyExistsError → command（409 语义由 API 层保留）、 AuthError / 认证类 → not_logged_in、 ConnectionError / TimeoutError → network（retryable）、 限流异常或 429 → rate_limited（retryable）。 映射表带保守兜底：未知异常归 command，不误报登录/权限。
  • 三件套契约保留：只读退避（限流 1s/4s/10s、网络 0.5s）、 诊断留痕（diagnostics() → /health/modal-cli）、 系统状态页错误分类全部不动；超时语义从「强杀子进程 + uncertain」改为 asyncio.wait_for 取消（远端状态同样不确定，错误文案保留 「先核对远端再重试」）。 退避分类机制需改造：现有 _is_read_only(args) 按命令串分类 （args[1] in _READ_ONLY_SUBCOMMANDS[args[0]]），类型化函数无命令串可分； 改为每个类型化函数内部声明只读性（_READ_ONLY_OPS 集合或装饰器）， 退避逻辑从命令串匹配迁到操作类型匹配。
  • 懒导入：import modal 收敛到 SDK 网关模块内部 （函数级或模块级按首次调用），避免 pytest 收集 / CLI 启动路径提前拉起 modal 配置； 1.5.5 实测 import 副作用仅「modal-client logger 配置 + 配置读取」， 无事件循环策略设置（旧 pyproject 注释里的说法过时，一并修正）。
  • 代理边界：CLI 路线在子进程 env 里摘掉 HTTP(S)_PROXY 并设 NO_PROXY=*；SDK 在主进程内不能全局改 env，改为 创建 client 时按 cli_env() 的同一边界处理（modal 客户端自身的 代理配置项或局部 env 快照），保证「Modal 云端通信不走本机代理」语义不变。

4.2 health 端点与前端契约变更

SDK 迁移后以下前端可见字段语义变化，不是「零改动」：

  • /health/modal-cli 的 path（CLI 可执行路径）： 前端状态页 status/index.tsx 第 128-130 行显示 data?.path 并带复制按钮。SDK 无可执行路径，该字段改为 "(in-process SDK)" 或空串， 前端展示文案从「CLI 路径」调整为「Modal SDK」。端点名 modal-cli 与 TS 类型 ModalCliHealth 暂不改名（避免 queryKey / 路由联动面扩大）， 但字段语义在批次 3 同步。
  • found（cli_path() 非空）：语义从「CLI 已安装」变为 「SDK 可导入」。deletion.py:324 的 if not cli_path() 守卫改为 if not sdk_available()。
  • cli_found（modal_volume.py:42、volume.py:76）： 前端 models/index.tsx:203 在 credentials_ok && !cli_found 时 显示「modal CLI 未安装」告警。字段名可保留，语义改为 SDK 可导入，告警文案同步调整。

5. 分批迁移计划

按「读 → 写 → 状态/账单 → 收尾」推进，每批独立提交、独立可回滚， 全程保持 REST 形态与错误 category 字段不变（前端路由 / queryKey 不感知）， 但 /health/modal-cli 的 path/found 与 cli_found 字段语义在批次 3 同步（见 §4.2）：

批次 1：SDK 网关 + 只读卷操作

  • modal_volume/client.py：client 生命周期、错误映射、懒导入、代理边界； list_dir / list_files / volumes_list 切 SDK。
  • 调用方：usage.py、deletion.py（卷存在性）、 volume.py _volume_exists；同步清掉这三处的 cli_json_list 用法。
  • 测试：SDK mock 层（unittest.mock 替换 SDK 句柄）重写 test_modal_volume_client.py 对应用例；语义差异用例 （listdir 根路径、mtime/size 类型）。

批次 2：卷写操作 + 分块上传落卷

  • put_file / put_directory / get_file / remove_file / volume_create / volume_delete。
  • 调用方：nodes.py（上传/移除/manifest）、settings_sync、workflows_sync、 executor（输入兜底通道）、uploader（最终落卷）、precheck、deletion（回收站）、 volume.py（卷 CRUD）、modal_volume/jobs.py、launch.py （_push_modal_args 的 volume put 独立子进程收敛进网关）。
  • 注意：staging 排除逻辑（.git/__pycache__）从 CLI 隐式行为确认后显式保留；--force 语义映射为「覆盖写」。
  • 测试：test_input_push / test_model_deletion / test_model_uploader / test_precheck / test_workflows_sync / test_m2_leftovers 的 CLI mock 同步。

批次 3：应用状态 + 账单

  • app_status（App.lookup）切 health 自检与 runner/client ensure_state；--version 自检改读 modal.__version__（或保留一次 CLI，见风险）。
  • billing_summary / billing_report 切 Workspace.from_context + ws.billing.*， Decimal → float 换算收敛在一处；缓存 120s/20s 保留。
  • 测试：test_health mock 同步；账单输出与 CLI 基线对照 （同一 workspace 同月，metered/billed 误差 < 0.0001）； test_version_align 的 test_run_deploy_passes_utf8_cli_env 因 deploy 保留 CLI 而有意保留，批次 4 确认仍绿。

批次 4：收尾 + deploy/run 决策

  • 删除 _popen / _run_once / cli_json_list / _unescape_cli_name / cli_env / _classify_error 的 CLI 路径（错误映射保留）； pyproject 依赖注释更新（modal 从「仅子进程调用」改为「SDK 直调 + 部署/流式作业/容器管理子进程」）； auth_env() 仅剩 deploy / run / container stop 三处 CLI 保留路径引用。
  • modal deploy 保留 CLI：镜像构建是长时构建操作， CLI 流式日志直通 job.log_tail；SDK App.deploy() 需要 importlib 加载 runner.py（本地导入副作用 + 日志面弱）， 收益不成比例。P2 可选项保留在本文档。
  • modal run 流式作业保留 CLI：downloads/moves 的价值就在 日志泵（进度 UI 实时性），SDK Function.remote() 不回传流式日志； P2 评估「函数调用 + 日志轮询」后另行立项。
  • container list/stop 保留 CLI：launch.py 的容器管理 与 deploy 同属运维语义；SDK Sandbox.objects.list() 存在但 container↔sandbox 同构性待验，P1 不冒险，P2 评估。
  • 文档同步：README 依赖注、本文件验收登记。

6. 风险与对策

风险对策
Windows 事件循环：uvicorn asyncio loop 与 modal grpclib 客户端共存未验证 批次 1 首个验证项：真机跑一次 listdir + health 自检，观察 "Event loop is closed / already running"；兜底方案：SDK 调用收敛到 独立 loop 线程（run_coroutine_threadsafe），语义不变。 实测依据：modal 1.5.5 import 不设事件循环策略，风险主要在运行期。
主进程 import modal 的副作用（modal-client logger、配置读取） 懒导入收敛在网关模块；logger 为独立命名空间，必要时 logging.getLogger("modal-client").setLevel(WARNING)； pytest 收集路径确认不触发网络调用。
多账号凭证切换：进程内 client 缓存与账号注册表联动 凭证对作为 client 缓存键；账号激活钩子重建 client； 切换期间在途调用允许完成（client 独立对象，不复用全局状态）。
语义差异引入回归：mtime 单位（CLI 文本 vs SDK int）、 size 类型（str vs int）、listdir 根路径、--force 覆盖、 staging 排除 差异清单显式列在批次 1/2 测试用例里；前端展示层 （大小/时间格式化）逐项过一遍 e2e。
错误分类漏判：SDK 异常类型比 CLI 文本更结构化，但部分错误 （服务端 5xx、限流）需确认异常形态 保守兜底（未知 → command）沿用；限流按异常信息匹配保留； 真机触发一次限流验证退避路径仍生效。

health 端点与前端契约变更：path/found/cli_found 字段语义变化， 前端状态页与模型页需同步 批次 3 显式处理（§4.2）：字段名保留、语义与文案更新； Playwright e2e 确认状态页与模型页不回归； 端点名 modal-cli / TS 类型 ModalCliHealth 暂不改名， 避免路由与 queryKey 联动面扩大。
